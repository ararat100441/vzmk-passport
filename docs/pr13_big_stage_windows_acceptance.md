# PR14 — Комплексный Windows E2E: многостраничные формы, PDF и релиз-кандидат

Версия исходников: ветка `fix/pr13-multipage-production`, потомок PR13.  
Цель: закрыть PR13 Excel Gate B visual FAIL **в одном комплексном задании**, не обрывая работу после каждой обычной ошибки.

## Подтверждённый baseline

Отчёт PR13 (24.10.2026): Word Gate A PASS (отдельная таблица УЗК с 8 колонками, Save/Open), Excel Gate B скрипт завершился техническим PASS, но просмотр всех 6 страниц показал VISUAL FAIL: **обрезанная шапка на третьих страницах обоих приложений**, а в АКЗ синтетические наименования накладывались/обрезались. Общая регрессия, полный Office E2E, сводный PDF и crash recovery не выполнялись. Исходные SHA и RC3 не изменены.

### Точно найденная программная причина

В `tests/production/verify_appendix_print_com.py` прежний diagnostic использовал `Range('A5:G114').RowHeight=18` для всех 110 строк, независимо от длины названия; `PrintTitleRows='3:4'` и количество страниц проверялись без анализа содержимого PDF. Поэтому технический PASS не означал пригодности печати.

Исходные XLSX ВЗМК (из ранее предоставленных образцов) имеют двухуровневые **объединённые** заголовки таблицы (горизонтальные/вертикальные объединения A3:A4, B3:B4 и прочие) и исходные высоты строк 3/4 около 15 пунктов. На повторяемых страницах такой высоты может быть недостаточно. Это гипотеза для практической проверки в Windows, **не утверждение, что визуальный дефект уже исправлен**.

## Изменения PR14

1. `production_app/office.py`: `fit_appendix_body()` включает WrapText для текстовых столбцов A/B, отключает сжатие, включает native Excel AutoFit для **реальной длины** каждой строки после вставки фактов, сохраняет остальные параметры; скрытые, объединённые и чрезмерно высокие строки вызывают STOP. Никакой фиксированной высоты 18 для всех марок.
2. `set_appendix_print_titles()`: повторяются только строка 3 либо строки 3–4. Заголовки с объединением получают минимально безопасные 28 пунктов в каждой строке только в выпускной/тестовой КОПИИ. Объект A2 не повторяется на следующих страницах.
3. `verify_appendix_print_layout()`: после Excel Save/ReadOnly Open проверяются **реальные высоты строк 3/4**, область печати и список повторяемых строк.
4. Word УЗК: отдельный нативный тест генерирует **60 синтетических соединений** для принудительного 3+ страничного документа, проверяет независимую 8-колоночную таблицу, повторяемость заголовка, число страниц, экспорт PDF.
5. Excel Gate B: 110 синтетических строк с **разной длиной** марок/наименований; вызывает тот же `fit_appendix_body()`, что производственный выпуск, и сохраняет PDF с **3+ страницами**.
6. PDF-аудит: анализирует каждую страницу на наличие заголовков/марок (при наличии доступного текстового слоя), обнаруживает пустые или неправильно разбитые страницы; `PENDING_VISUAL_REVIEW` вместо ложного технического PASS.
7. Тесты: регрессия визуальной третьей страницы, высот заголовка, AutoFit, длинных/скрытых/объединённых строк, наличия марок на каждом листе.

## Обязательный комплексный цикл (ОДНО задание Codex)

### G0. Безопасное начало

- Создать отдельный Windows worktree именно от commit ветки PR14. Не изменять PR13 и старые worktree.
- Найти уже использовавшиеся в PR12/PR13 **те же самые** проверенные Word/Excel-шаблоны, ВОМ и DEV-копии. Сверить SHA-256 перед использованием.
- Источники, актуальную RC3, `main` и рабочий реестр не трогать.
- Все диагностические каталоги должны быть новыми; никаких overwrite прежней экспертизы.

### G1. Native Word + Excel (обязательная визуальная приёмка)

В Windows PowerShell/Codex терминале:

```powershell
py -3.12 -B tests/production/verify_uzk_word_com.py --template "<точный исправленный УЗК.docx>" --output "<НОВАЯ_папка_Word_PR14>"
py -3.12 -B tests/production/verify_appendix_print_com.py --appendix-one "<Приложение №1.xlsx>" --akz-appendix "<адаптированный АКЗ-приложение.xlsx>" --output "<НОВАЯ_папка_Excel_PR14>"
```

Оба прогона должны создать Word/Excel/PDF и JSON. Код проверки возвращает `PENDING_VISUAL_REVIEW`, **не** PASS. Codex обязан открыть изображения **каждой страницы** обоих Excel PDF и многостраничного Word PDF. Проверить: шапку 3-й страницы, отсутствие обрезки/наложений, читаемость семи столбцов и длинных имён, повтор заголовка УЗК на страницах 2+, корректную ориентацию и отсутствие пустых страниц.

Если визуально FAIL, **не останавливайся на обычной ошибке**: воспроизведи, найди корневую причину, исправь адресно только в новой ветке (или в её дочерней ветке), дополни тест, повтори G1. **До 5 циклов исправления** в пределах текущего задания; не ухудшать другие формы.

### G2. Общая регрессия Windows

После визуального PASS запусти **ВСЕ** существующие тесты программы одним запуском (включая Win32 safety, Word, Excel, PDF и новые PR14). Нужно 0 FAIL/ERROR. Обычные функциональные FAIL адресно исправляй, коммить и повторяй весь набор; не скрывай FAILED и не объявляй выборку тестов эквивалентом полной регрессии.

### G3. Полный Office E2E

Только в тестовом контуре: CHECK → PREPARE → VERIFY → CONFIRM → RELEASE → COMMIT → READBACK → COMPLETE. Взять известные проверенные источники. **Никаких придуманных результатов ВИК/УЗК/АКЗ в официальном режиме**; тестовые значения — только в явно изолированной синтетической сессии, документы помечены как учебные. Все ключевые исходники и рабочий реестр остаются read-only. 

Проверить каждую форму Word/Excel и общий PDF: документ о качестве → Приложение №1 → ВИК → УЗК → акт АКЗ → приложение АКЗ. При нескольких вариантах АКЗ — соответствующие пары в установленном порядке. Проверить итоги, формулы, средние, слои, названия, даты, номера, отсутствие старых результатов и совпадение имени PDF с папкой.

Обычные программные ошибки устранять автономно и повторять E2E **до общего лимита 5 циклов исправления** (совместно с G1/G2). Если нужно **согласование макета** или новые фактические сведения — не придумывать, оформить блокер и STOP.

### G4. Recovery и тестовый EXE (если G1–G3 PASS)

- На дополнительных одноразовых копиях проверить crash-recovery при допустимых fault-injection; не имитировать сбой в реальном Office/реестре.
- Сверить SHA исходников и убедиться в отсутствии чужих/осиротевших Office процессов.
- Если все проверки PASS, собрать отдельный временный Windows **релиз-кандидат для smoke**, проверить старт Tkinter, выбор проекта, загрузку документов, тренинговый цикл, PDF. Не устанавливать поверх RC3, не копировать в production и не объявлять релиз 1.0.0 без финального разрешения.

## Когда немедленно STOP

- SHA рабочего или исходного файла изменился / возможна запись в реальный реестр.
- Требуется проставить неподтверждённые значения контроля, сварщиков, результатов испытаний или подписей.
- Нужна переработка утверждённого формуляра сверх технической разметки печати.
- Не хватает подтверждённых первичных входов или доступ к точной копии утрачивается.
- Получено 5 незакрытых циклов исправлений, выявлена неизвестная опасность потери данных.
