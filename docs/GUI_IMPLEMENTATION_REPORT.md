# ВЗМК — утверждённый GUI: реализация

**Статус: GUI CODE READY FOR WINDOWS VERIFICATION / EXE NOT BUILT.**

Дата: 03.11.2026.

Основа: `design/approved-vzmk-gui` (от аудированной review-ветки).
Только визуальные изменения: `production_app/gui.py`,
`docs/APPROVED_GUI_DESIGN.md` и новый smoke-тест
`tests/production/test_gpt6_approved_visual_gui.py`.

## Что сделано

- Единая светлая палитра (#F7F9FC, #FFFFFF) с тёмно-синим
  акцентом (#183B63) и шрифтом Segoe UI через стандартный
  Tkinter/ttk `clam` — без новых зависимостей.
- Верхняя панель с символом здания, названием ВЗМК и существующей
  кнопкой настроек.
- Группы 01 «Данные паспорта», 02 «Отгрузочная ведомость»,
  03 «Документы и контроль».
- Четыре карточки показателей (марки, изделия, масса, площадь).
  Отображаемые значения разбираются из **уже существующей**
  `Shipment.summary()`, без нового вычисления массы/площади.
  Пустая/неизвестная площадь отображается как «не указана» или «—»,
  не как ноль.
- Одна контрастная главная кнопка «Сформировать пакет» с прежней
  командой `self.check`.
- Журнал операций в отдельной секции, добавлена вертикальная прокрутка,
  при этом `self.write` и все сообщения остались прежними.
- Визуальная тема применяется также к существующим ttk-компонентам
  дочерних окон без изменения их логики.

## Подтверждённая неизменность

При сопоставлении исходных файлов GitHub:

- Исходный `App` имел **45 методов**. Все прежние методы, кроме
  `__init__`, сохранили исходный текст без изменений.
- Новые методы/функции исключительно оформительские:
  `App.update_vom_kpis`, `apply_visual_theme`.
- Методы `check, prepare, verify, confirm, release, commit, readback,
  complete, recover` и все обработчики не редактировались этой веткой.
- Сохранены элементы `self.projects`, `self.numbers`,
  `self.new_widget`, `self.vom_widget`, `self.source_numbers`,
  `self.shipment_label`, `self.shipment_entry`, `self.progress`,
  `self.log` и `self.buttons[0]`.
- Не менялись `core.py`, `storage.py`, `coordinated.py`,
  формы/расчёты, требования, PyInstaller spec, Excel или PDF.
- Исходная GUI-версия из этой линии уже использует выпуск без
  предварительного PDF с **одним подтверждением**.
  Это поведение не добавлялось и не менялось данной визуальной правкой.

## Проверка и условия приёмки

Добавлены четыре теста Windows Tk:
1. Все прежние команды и элементы доступны.
2. Все четыре секции присутствуют.
3. Данные существующей сводки ВОМ отображаются без нового пересчёта.
4. Тема и журнал с полосой прокрутки работают.

Проведена локальная проверка совместимости основных `ttk` styles
и `ttk.Label.configure(state=...)` в Tcl/Tk 8.6 под Linux/Xvfb.
**Это не полный Windows GUI-тест и не тест этого EXE.**

До приёмки обязательно:
- Запустить на Windows 11/Office `python -m unittest
  tests.production.test_gpt6_approved_visual_gui -v`
  или соответствующий файл из `tests/production`.
- Проверить внешний вид и доступность элементов на экране
  1366×768 при 100%, 125% и 150% масштаба.
- Проверить неизменность существующих команд, состояния блокировки,
  Tab-навигацию, скроллинг и предупреждения об ошибках.
- Пройти согласованный полный DEV выпуск, native readback → COMPLETE
  на копиях Excel с изолированным `.vzmk-operations`; рабочий
  реестр не изменять.
- Только затем собрать отдельный PyInstaller EXE и зафиксировать SHA-256.

**Главный риск:** новая ветка наследует непроверенные Windows изменения
из review/audit источника (Hardlink/readback и отмена предварительного
PDF). Внешнее оформление не доказывает их исправность. Текущую
незавершённую рабочую операцию не трогать без отдельной проверки.


## CODEX51 — исправление запуска без настроенного реестра (03.11.2026)

- CODEX51 сообщил **BLOCKED**, не собрал EXE: первый Windows Tk-тест
  завис на модальном сообщении после `KeyError('registry')`.
- Корневая причина подтверждена из исходников и минимального Tk 8.6
  воспроизведения: для пустого `ttk.Combobox` свойство `values`
  возвращает строку `''`, а выражение `'' in ''` даёт `True`.
  Инициализация неверно вызывала `select_project()` при пустом профиле.
- Исправление исключительно в `App.__init__`: выбор проекта вызывается
  только при непустом имени и настроенном реестре, после проверки
  наличия проекта среди значений Combobox. Отложенный запуск окна
  «Настройки путей» при отсутствии реестра оставлен без изменений.
- Тест `test_gpt6_approved_visual_gui.py` дополнен проверками первого
  запуска с пустыми настройками и сохранности автозаполнения при
  корректном настроенном проекте (всего шесть GUI-тестов).
  Для исключения зависания CI тестовая инициализация подменяет
  `messagebox.showerror` явным AssertionError.
- Не изменены формы, данные, учёт, обработчики выпуска, восстановление
  и содержимое текущей рабочей операции.
- **Новая версия ещё не проверена полным Windows-тестом и не собрана.**
  Повторить CODEX51 из нового HEAD ветки; локальные workbooks не трогать.

## CODEX51 — GUI smoke 5/6 (повторный Windows-прогон)

Отчёт Codex: из шести GUI-тестов пять прошли, включая первый запуск с
пустыми настройками. Шестой тест проверял `widget.cget('state') == 'readonly'`,
но Tkinter 8.6 на Windows возвращает `_tkinter.Tcl_Obj` со строковым
представлением `readonly`. Это некорректное предположение **теста**,
а не доказанная ошибка combobox.

Исправлено **только** `tests/production/test_gpt6_approved_visual_gui.py`:
- три проверки state приведены к `str(widget.cget('state'))`;
- обработчик `root.after(300,self.settings)` во время инициализации в
  тесте перехватывается без фактического планирования, поэтому скрытый
  `Tk` не может вызывать окно настроек после destroy;
- тест явно проверяет, что окно настроек было запланировано;
- второй экземпляр GUI для настроенного проекта теперь создаётся внутри
  `Toplevel`, а не повторно на том же корневом окне.

Поведение `Tcl_Obj` отдельно воспроизведено в Tcl/Tk 8.6 на Linux с Xvfb.
Повторный нативный Windows-прогон после этих изменений ещё не выполнен.
Новый EXE не собран. Рабочие файлы не изменялись.

## CODEX51 — закрытие дефекта компоновки окна «Отгрузочная ВОМ»

Отчёт Codex: все 6 GUI-тестов PASS. Полный DEV-прогон остановлен
**до записи**: у редактора семиколоночной ВОМ кнопки «ОК», «Отмена»
и «Удалить строку» оказались за нижней границей окна. EXE не собран,
рабочие и изолированные Excel не менялись. Оставшийся адресный
набор 83/84 имеет ещё одну проблему *самого теста* (заглушка вместо
проверяемого метода), которую CODEX51 подтвердил только исправлением
в памяти; её точный исходник здесь не сообщён и наугад не менялся.

Причина скрытых кнопок непосредственно видна в исходнике:
`shipment_dialog.open_shipment()` размещал `Treeview(height=20)`
с `fill='both', expand=True` **раньше**, чем нижнюю панель. При
ограниченной высоте Windows/DPI менеджер `pack` мог выделить
доступное пространство дереву и вытеснить кнопки.

Правка **только геометрии**, в `production_app/shipment_dialog.py`:
- панель из трёх прежних кнопок и строка статуса резервируют место
  у нижнего края **до** размещения растягивающейся таблицы;
- стартовая высота `Treeview` уменьшена с 20 до 7 видимых строк
  при сохранении вертикальной прокрутки;
- обработчики вставки, удаления, ОК, сохранения XLSX и закрытия
  не менялись, новых кнопок/действий нет.

Добавлен Windows GUI-регрессионный тест
`tests/production/test_gpt6_vom_dialog_layout.py`: проверяет
наличие кнопок, их положение внутри окна высотой 360 и 420 px,
место нижней панели и разрешение вертикальной прокрутки таблицы.

**Состояние:** SOURCE FIXED / WINDOWS TEST NOT RUN / EXE NOT BUILT.

Дополнительное изолированное воспроизведение геометрии в Tk 8.6/Xvfb
(Linux, экран 1366×768) сравнило старый и новый порядок pack:
при высоте 350, 410 и 500 px и масштабах Tk 1.3333, 1.6667, 2.0
старые три кнопки оставались **не отображёнными**, новые все три были
отображены и помещались в границы окна. Это проверка компоновки,
а не фактический Windows GUI/E2E и не тест нового EXE.
Для завершения CODEX51 необходимо обновить локальную изолированную
копию до нового HEAD, повторить GUI-тесты, восстановить полный DEV
сценарий и только после PASS собрать EXE. Не изменять рабочие Excel
или реальные незавершённые операции.

## CODEX51 — stale сводка ВОМ после удаления (следующий Windows blocker)

Codex в изолированном DEV-окне вставил 3 изделия общей массой 842,92 кг,
удалил `К1-3` и обнаружил устаревшую сводку 3 шт./842,92 кг при наличии
только двух строк таблицы. Кнопки стали видимы; 2/2 теста компоновки PASS,
6 предыдущих GUI-тестов PASS. Текущий DEV-цикл остановлен до записи,
рабочие Excel не изменены, EXE не собран.

Причина: `shipment_dialog.remove()` удалял элементы Treeview, но
не пересчитывал текст `status`; аналогичная проблема была возможна при
редактировании отдельной ячейки. Исправлено в
`production_app/shipment_dialog.py`:
- единая `update_status()` заново читает *текущие* строки Treeview и
  применяет существующие `normalize().summary()` без альтернативной
  арифметики;
- обновление выполняется после первоначальной загрузки, Ctrl+V,
  удаления и применения правки ячейки через существующий `on_change`;
- пустая таблица показывает «ВОМ пуста»; частично неверная строка
  показывает «ВОМ требует исправления», **не старые валидные итоги**;
- метод «ОК» сохраняет только текущие строки как раньше.
- существующая логика принятия, сохранения XLSX и отмены не менялась.

Адресные Windows тесты `test_gpt6_vom_dialog_layout.py` расширены:
первичная компоновка, полная видимость кнопок, удаление одной строки,
удаление всех строк, неправильное редактирование количества,
«ОК» с проверкой приватного XLSX, «Отмена» без записи.
Итого **семь** тестов в этом файле; ещё не запускались на Windows
после исправления.

Дополнительно исправлен известный дефект
`test_gpt6_direct_issue.py::test_issue_seals_direct_mode_without_claiming_pdf_review`:
вместо подменённого fixture-объекта `a.issue = Mock()` вызывается
`gui.App.issue(a)` для проверки настоящей логики.
CODEX51 подтвердил 84/84 только с аналогичной заменой **в памяти**;
теперь это исправлено в GitHub. Никакой бизнес-логики не затронуто.

Изолированная проверка механики Tkinter с теми же входными числами:
3 шт./842,92 кг/26,877 м² → удаление одной строки →
2 шт./542,92 кг/16,877 м²; неверная ячейка → сообщение об ошибке;
пустой список → «ВОМ пуста». Успешный результат проверки
**не является Windows GUI E2E или испытанием готового EXE**.

Для завершения CODEX51 следующий исполнитель должен провести **единый**
полный Windows DEV-прогон из нового HEAD. Мелкие UI/test-only находки,
если их безопасно устранить в изолированном дереве, исправлять и
перезапускать в рамках **этой же** задачи, а не требовать от владельца
нового короткого задания на каждую. Но **STOP обязателен** при риске
повреждения рабочих Excel, несоответствии SHA, подмене данных, опасной
смене логики или несостоятельном DEV native readback.
